# Выкатка модели комиссии — раннбук

Пять шагов. Три из них трогают цепь. **Порядок несущий**: у четырёх шагов из
пяти неверная очерёдность стоит денег, рассылает людям неправду или тратит газ
впустую.

Составлен 30 июля 2026. **Выполнен целиком в тот же день** — все пять шагов
прошли, результат каждого сверен чтением с цепи. Итоги и адреса:
`docs/2026-07-30-itogi-s-novogo-diamanta.md`.

Документ оставлен как есть, а не переписан в прошедшем времени: он ещё
понадобится для отката и как образец для следующей выкатки. Проверки после
каждого шага и разбор «что будет при падении на середине» верны независимо от
того, сделан шаг уже или нет.

Этот документ **заменяет** `docs/RUNBOOK-dispute-settlement.md` там, где они
расходятся: два шага того раннбука наш cut поглощает целиком (см. «Что НЕ
запускать»). Читай этот, а тот — только ради разбора экономики споров.

Перед каждым шагом с цепью — сначала **сухой прогон** без `--broadcast`.
Скрипты останавливаются на пре-флайте до траты газа, если состояние цепи не то,
которое ожидалось. Обходить проверку нельзя: она и есть смысл пре-флайта.

## Шаг 1. Фронт и релеер

```bash
bash deploy-local.sh --all
```

**Почему первым — а не «заодно».** Интерфейс и контракт расходятся
несимметрично, и одна из двух сторон расхождения безопасна, а другая нет.

Контракты первыми: фронт подписывает permit на `amount`, а контракту нужен
`amount + fee`. `transferFrom` падает **после** двух подписей пользователя —
он подписал, заплатил вниманием, получил ревертнувшую транзакцию. Плюс `fee`
читается через `??`-фолбэк на захардкоженную региональную таблицу, то есть
интерфейс не сообщит об ошибке, а **молча покажет стухшую цифру**. Плюс чек
сделки печатает комиссию, которой протокол уже не берёт.

Фронт первым: всё падает закрыто. `feeConfigReady` видит, что `getFeeBps` и
`getFeeFloor` ещё не смонтированы, кнопки заблокированы, вместо суммы стоит
`—`, и до подписи дело не доходит вообще.

Этот же деплой везёт интерфейс дележа спора (`frontend/src/lib/settledRefund.ts`).
Без него первый же дележ разошлёт обеим сторонам «сделка отменена, деньги
возвращены клиенту» — включая того, кто получил половину. Пуш живёт в шторке
уведомлений, его не отзовёшь.

**Проверить после:** открыть постинг заказа. Сумма комиссии должна считаться и
показываться; если стоит `—`, значит чтение конфига не прошло — это ожидаемо до
Шага 3 и обязано пропасть после него.

## Шаг 2. Сабграф v2.3.0

```bash
cd subgraph && npm run deploy:studio     # метка -l v2.3.0
```

**Почему до цепи, а не после.** Выкатить раньше контрактов совершенно
безопасно: сабграф просто слушает события, которых пока не бывает. Выкатить
позже — значит оставить окно, в котором индекс уже расходится с цепью.

**Одна выкатка закрывает три зависимости.** В дереве сейчас v2.3.0, и в
манифесте прописаны все хендлеры:

- `handleFeeCollected` — сущность `FeeCollection`, разбивка дохода по шести
  видам (`subgraph/subgraph.yaml:58`, `subgraph/src/diamond.ts:216`);
- `handleDisputeSplitNoVerdict` — тот, что числится невыкаченным блокером в
  `docs/OPEN-ITEMS.md` п. 8 (`subgraph/subgraph.yaml:97`,
  `subgraph/src/agreement.ts:91`);
- `handleDisputeResponded` и `handleDisputeUnanswered` плюс поля явки
  (`clientResponded`/`executorResponded`) — правило явки Шага 5. **Без них
  сделка, закрытая таймаутом без отклика, висит в статусе спора во всех
  интерфейсах**, хотя на цепи финализирована и пуста: исход опознаётся по
  событию, а не по статусу.

Хендлер дележа нарезали раньше под меткой v2.1.0, но v2.1.0 никогда не
выкатывался, а метка перезаписана — отдельного артефакта v2.1.0 больше нет. То
же произошло с v2.2.0. Поэтому **`npm run deploy:studio` публикует всё разом**,
и блокер пункта 8 снимается этим шагом, а не отдельным.

> ⚠️ Метки `v2.1.0`/`v2.2.0` остались в документации в нескольких местах,
> включая `docs/RUNBOOK-dispute-settlement.md:50`. Команда там сегодня
> опубликует v2.3.0 и утащит всё вышеперечисленное — не потому, что кто-то
> ошибся, а потому что метка одна на дерево.

**Что деградирует, если этот шаг отстанет от Шага 3:** леджер дохода читается из
`AgreementDeployed.fee` — пересчёта `quote()` на момент найма, а не реально
удержанного. На прямом найме числа совпадают, на досках расходятся: настоящие
деньги там `jobFeeHeld`/`requestFeeHeld`, удержанные при **постинге**.
Деградирует аналитика, не статусы и не деньги: `FeeCollection` не читает ни один
интерфейс.

Задержка не теряет историю навсегда — `subgraph.yaml` держит
`startBlock: 44613049`, новая версия доиндексирует задним числом. Плата за
задержку — окно неверного леджера, не дырка в данных.

**Проверить после:** запросить `feeCollections(first: 1)` — сущность должна
существовать (пустой список это нормально, ошибка схемы — нет).

> Записи о реально задеплоенной версии в репозитории нет нигде: ни
> deployment-id, ни хеша, endpoint приколочен к `/version/latest`. Последняя
> версия с подтверждением выкатки — v2.0.0. Определить с цепи, что крутится
> сейчас, невозможно в принципе.

## Шаг 3. Cut модели комиссии

```bash
# сухой прогон
forge script script/UpgradeFeeModel.s.sol --rpc-url https://sepolia.base.org -vvv

# боевой
forge script script/UpgradeFeeModel.s.sol \
  --rpc-url https://sepolia.base.org --private-key $PRIVATE_KEY --broadcast -vvv
```

Шесть новых фасетов, один `diamondCut` из десяти элементов: Replace 106
существующих селекторов + Add 14 новых, **плюс засев конфига той же
транзакцией** через `_init` = адрес свежей реализации `FactoryFacet`,
`_calldata` = `initFeeModel(500, 1_000_000, 5)`.

**Почему засев обязан быть в той же транзакции.** Сразу после cut'а `feeFloor`
равен нулю, а `FactoryStorage.quote()` на нуле ревертит `FeeNotConfigured`. Её
зовут `mintJob`, `mintJobWithPermit`, `requestService`, `requestServiceWithPermit`
и оба прямых пути фабрики. Отдельная транзакция засева означала бы окно, в
котором **ни один денежный путь не работает**, включая приём уже опубликованных
живых заказов.

**Почему один cut, а не шесть.** Доски зовут `quote()` напрямую. Разбей cut на
фасеты — и между ними будет окно, где новая доска зовёт старую фабрику без
`quote()` либо наоборот.

### Что этот шаг везёт помимо комиссии

Не «заодно», а к сведению — оба пункта вступают в силу немедленно:

1. **Гейты закрытия окна вердикта** в уже существующие `claimDispute` и
   `releaseDispute`. Клеймить и освобождать спор после закрытия окна станет
   нельзя. Старые клоны это не ломает: гейт читает `disputedAt()` и
   `DISPUTE_WINDOW()`, оба присутствуют в байткоде живой реализации — проверено.
2. **Три селектора сбора за спор** (`creditDisputeFee`, `getTreasurySlice`,
   `withdrawTreasurySlice`) монтируются и готовы принимать деньги, но звать их
   пока некому: считает и переводит сбор `Agreement`, а он меняется только на
   Шаге 5. Начисления не будет — `creditDisputeFee` требует, чтобы вызывающий
   был зарегистрированным агриментом, а их ноль.

### Пре-флайт — четыре проверки, каждая до траты газа

Диамонд не ноль и с кодом; `owner() == broadcaster`; все шесть старых фасетов
найдены с ожидаемым числом селекторов; **`feeFloor` на цепи равен нулю**.

Последняя читается сырым чтением слота (`FACTORY_STORAGE_POSITION + 9`), а не
геттером: `getFeeFloor()` — сам один из 14 добавляемых селекторов, до cut'а его
физически нечем вызвать. Смещение загейчено пятью тестами в
`test/UpgradeFeeModelSelectors.t.sol`, включая отрицательный контроль на соседние
слоты.

Если `feeFloor` окажется ненулевым — **останавливайся и разбирайся**.
`initFeeModel` одноразовый, на ненулевом поле он ревертит `AlreadyInitialized` и
утащит за собой весь cut.

### Проверить после — с цепи, не по логу симуляции

```bash
D=$DIAMOND_ADDRESS; R=https://sepolia.base.org
cast call $D "getFeeBps()(uint256)"             --rpc-url $R   # 500
cast call $D "getFeeFloor()(uint256)"           --rpc-url $R   # 1000000
cast call $D "getMaxPendingRequests()(uint256)" --rpc-url $R   # 5
cast call $D "quoteFee(uint256)(uint256)" 200000000 --rpc-url $R   # 10000000
cast call $D "getAllFees()"                     --rpc-url $R   # ДОЛЖЕН ревертить
```

Скрипт проверяет то же сам, плюс что все шесть старых адресов держат ноль
селекторов и что общее число маршрутизируемых селекторов выросло ровно на 14
(145 → 159).

`getAllFees()`, который **не** ревертит, означает, что cut не применился —
региональные комиссии сняты именно этим шагом.

## Шаг 4. SVGRenderer — сразу за Шагом 3

```bash
forge script script/UpgradeSvgRenderer.s.sol \
  --rpc-url https://sepolia.base.org --private-key $PRIVATE_KEY --broadcast -vvv
```

Разворачивает новый `SVGRenderer` и подставляет его через
`JobReceiptFacet.setSvgRenderer`. Диамонд зовёт рендерер `staticcall`-ом, так
что это не `diamondCut`, а одна обычная транзакция.

**Почему сразу.** Между Шагами 3 и 4 каждый минтящийся чек-NFT печатает
**неверную комиссию**: живой рендерер выводит строки `PPP FEE` и `TOTAL` со
стухшими региональными числами, которых протокол уже не берёт. Новый печатает
только `ESCROW` — сумму эскроу. Косметика, самоисправляется на следующем
рендере, деньги не трогает — но это неправда на артефакте, который человек
сохраняет себе.

**Проверить после:**

```bash
cast call $DIAMOND_ADDRESS "getSvgRenderer()(address)" --rpc-url https://sepolia.base.org
```

Скрипт дополнительно печатает вывод нового рендерера на образцовых данных —
глазами проверить, что есть строка `ESCROW` и нет `PPP FEE` / `TOTAL`.

## Шаг 5. Реализация `Agreement`

> ✅ **ВЫКАЧЕН 30 июля 2026.** Задержка была ради правила явки
> (`docs/superpowers/specs/2026-07-30-empty-dispute-response-rule-design.md`) —
> правило реализовано, и в реализации, которую разворачивает этот скрипт, оно
> уже есть. Причина задержки остаётся в силе как **требование к порядку**:
> `totalAgreements()` = 0, а любая сделка, созданная между двумя выкатками
> эталона, навсегда остаётся с тем правилом таймаута, которое действовало при её
> создании — клон несёт свою реализацию намертво. Поэтому эталон меняется **один
> раз**, с правилом явки внутри, а не дважды.
>
> Из этого же следует, что Шаг 2 (сабграф v2.3.0) — не «заодно», а условие: без
> его хендлеров сделка, закрытая таймаутом без отклика, висит в статусе спора во
> всех интерфейсах.

```bash
forge script script/UpgradeAgreementDisputeFee.s.sol \
  --rpc-url https://sepolia.base.org --private-key $PRIVATE_KEY --broadcast -vvv
```

Разворачивает новую реализацию `Agreement`, новый `AgreementDeployer(diamond,
impl)` и подставляет его через `setAgreementDeployer`. Новый деплойер нужен
потому, что `implementation` в нём `immutable` — подменить реализацию у
существующего деплойера нечем.

**Это не миграция.** Клоны EIP-1167 намертво несут адрес своей реализации в 45
байтах; перевести существующий клон на другую реализацию нельзя ничем. Шаг
переключает то, **из чего чеканятся будущие сделки**.

**Почему это шаг того же окна, а не «потом».** В задеплоенной реализации живёт
открытая экономическая дыра: клейм спора добровольный и бесплатный, поэтому
клиент открывает спор, ждёт `DISPUTE_WINDOW` (4 дня), никто не берётся — и по
таймауту клиент получает **весь котёл, оставшись с работой**. Исполнитель
получает ноль.

В новой реализации исход того же таймаута решает **явка**, а не одно правило на
все случаи (`src/Agreement.sol`, `triggerArbiterTimeout`):

- откликнулись **оба** (`respondToDispute`, а поднявшему флаг ставит сам
  `raiseDispute`) — котёл **пополам**, `floor(pot/2)` исполнителю, остаток
  клиенту, событие `DisputeSplitNoVerdict`;
- **одна сторона молчала** всё окно — ей **четверть** котла, остаток
  явившемуся, событие `DisputeUnanswered(responder, toResponder, toSilent)`.

Оба события несут **фактически переведённые** суммы: если USDC заблокировал
получателя, недоставленная доля уходит клиенту, и событие показывает ноль. На
этом держатся и уведомления, и сабграф — поэтому Шаг 2 обязателен.

Отсрочка этого шага не откладывает риск, а гарантирует его: сегодня
`totalAgreements()` = 0, то есть раскалывать нечего, а каждая сделка, созданная
до подмены, останется с этой дырой **навсегда**. Задним числом не починить.

**Раскладка хранилища `Agreement` изменилась** — правило явки дописало два поля,
`clientResponded` и `executorResponded` (снапшот
`script/agreement-layout.snapshot`, 30 строк вместо 28; оба легли в один слот
25). Изменение **append-only**, ни одно существующее поле не сдвинулось и не
поменяло тип, гейт `script/check-agreement-layout.sh` зелёный. Для этого шага
рисков хранилища нет и по второй причине: клон несёт раскладку своей
реализации, а существующих клонов ноль. Но утверждать «раскладка не менялась» —
это ровно тот класс утверждения, который в июле 2026 сломал живой JobBoard, так
что сверяйся со снапшотом и гейтом, а не с этим абзацем.

**Пре-флайт этого скрипта нельзя пройти до Шага 3**: он требует, чтобы
`facetAddress(creditDisputeFee)` был ненулевым, иначе боевой запуск невозможен
(сухой прогон проходит). Порядок гарантирован кодом, а не памятью.

**Проверить после:**

```bash
D=$DIAMOND_ADDRESS; R=https://sepolia.base.org
NEW=$(cast call $D "getAgreementDeployer()(address)" --rpc-url $R)
echo $NEW                                                    # НЕ 0x8639…5B2b
cast call $NEW "implementation()(address)" --rpc-url $R       # НЕ 0xf7cBecE7…
cast call $NEW "authorizedCaller()(address)" --rpc-url $R     # == $D
```

Третья проверка не формальность: деплойер с чужим `authorizedCaller` молча
перестанет создавать сделки.

## Что НЕ запускать

Два скрипта из `docs/RUNBOOK-dispute-settlement.md` наш cut поглощает. Оба
безвредны при попытке, но время потратят.

**`UpgradeArbiterRegistryDisputeFee.s.sol` — лишний и незапускаемый.** Его
эффект (Replace 44 + Add 3 из того же `HEAD`-исходника) — подмножество Шага 3.
После cut'а на арбитр-фасете станет 47 селекторов, и скрипт упадёт на пре-флайте
`"unexpected selector count on the live facet - stop and look"` — до
`vm.startBroadcast`, без единого вея.

**`UpgradeFactoryFacetDisputeGate.s.sol` — поглощён целиком.** Чистый Replace 13
селекторов фабрики; Шаг 3 делает то же и ещё 8 добавляет. Вдобавок скрипт
печатает комиссии семи регионов, которых после Шага 3 не существует, и трактует
ноль как поломку — то есть будет пугать оператора несуществующей проблемой.

## Откат

**У каждого скрипта своя инструкция, и он печатает её сам после успеха.** Читай
её из вывода, а не отсюда: там подставлены живые адреса. Три вещи стоит знать
заранее.

**Никогда не откатывай `Replace`-ом селекторы, которых у целевого фасета нет.**
`DiamondProxy.replaceFunctions` сверяет только, что фасет **другой** и что у него
есть хоть какой-то код. Реализует ли он селектор — не проверяется никогда. Такой
кат **проходит успешно**, loupe показывает селектор смонтированным, а каждый
вызов ревертит с пустым returndata: невидимо для мониторинга уровня фасетов. Для
снятия селектора есть `Remove` (action 2, `facetAddress` обязан быть нулём —
`src/DiamondProxy.sol:194`).

Практически: откат Шага 3 — это один `diamondCut`, где шесть групп Replace
возвращаются на старые адреса **и в том же кате** 14 добавленных селекторов
снимаются через `Remove`.

**Откат Шага 4 в одиночку неверен.** Он вернёт стухшую региональную таблицу на
каждый чек — это правильно только если откатывается и Шаг 3.

**Откат Шага 5 неполон по конструкции.** Клоны, отчеканенные между выкаткой и
откатом, остаются на новой реализации навсегда. Ничего не ломается: подмена
деплойера возвращает старое поведение только **новым** сделкам. Команда:

```bash
cast send $DIAMOND_ADDRESS "setAgreementDeployer(address)" \
  0x863923769FBEFB5da6C4657d6f9aE7D900965B2b \
  --private-key $PRIVATE_KEY --rpc-url https://sepolia.base.org
```

## Падение на середине

**Шаг 3, крах между деплоями фасетов.** Шесть `CREATE` идут отдельными
транзакциями до cut'а. Уже намайненные фасеты лежат задеплоенными и
неподключёнными — потерян только газ. Диамонд продолжает обслуживать людей на
старых фасетах. Повторный запуск просто разворачивает шесть свежих; чистить
нечего.

**Шаг 3, реверт самого `diamondCut`.** Все десять элементов и
`_init.delegatecall` — одна атомарная транзакция. Состояния «часть фасетов
заменена, часть нет» не существует.

**Шаг 3, падение post-flight после успешного ката.** Уже намайненный cut этим не
отменить — post-flight только сигнализирует оператору. Свойство любого
broadcast-скрипта, а не дефект.

**Шаг 4, крах между деплоем рендерера и `setSvgRenderer`.** Новый рендерер лежит
неиспользованным, фасет продолжает `staticcall`-ить старый. Полусломанного
состояния нет.

**Шаг 5, крах между деплоями и `setAgreementDeployer`.** Новая реализация и новый
деплойер лежат неподключёнными, фабрика продолжает чеканить со старого. Потерян
газ, состояние целое.

## Что остаётся открытым после выкатки

Не блокеры, но знать до, а не после — `docs/OPEN-ITEMS.md`:

- **пп. 9-11** — дележ можно сбить в сговоре с арбитром: он клеймит спор внутри
  окна и молчит. Бесплатные обходы закрыты, платный остался. Лечится жизненным
  циклом клейма, а не гейтами — тема брейншторма по экономике арбитров;
- **п. 2** — ступени 2 и 3 лестницы казны живыми деньгами не проверены;
- **п. 18** — `npm run lint` не работает во всём репозитории;
- диамонд остаётся апгрейдируемым с одного ключа. Решение принято сознательно
  (полная неизменяемость лишила бы будущую команду возможности починить
  денежный баг, а их в этой ветке нашлось несколько), но `DiamondCut`-событие
  пока никем не отслеживается, и копирайт про «отсутствие администраторов»
  этого не отражает.
