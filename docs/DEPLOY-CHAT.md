# Выкатка чата на сервер

**Составлено 8 августа 2026.** Всё, что здесь написано, проверено замером на
двух настоящих серверах, а не придумано.

Адрес сервера в командах — `root@IP_VPS`. Подставь настоящий (он в `.env`,
переменная `VPS`), в репозиторий его не вписывай: сервер стоит за туннелем
Cloudflare, и весь смысл туннеля в том, что настоящий адрес никто не знает.

---

## Самое главное, в двух словах

На сервере живут **две части**: сервер-посредник (мы зовём его релеер) и сам
сайт. Обновлять надо **сначала посредника, потом сайт**.

**Почему такой порядок.** Новый сайт умеет разговаривать только с новым
посредником: на старом нет справочника ключей, и чат просто не откроется.
А новый посредник со старым сайтом уживается прекрасно — старый сайт про него
и не знает, его чат работал через чужую сеть.

Значит: перепутаешь порядок — чат будет мёртв всё время, пока едет вторая
половина. Сделаешь по порядку — люди ничего не заметят.

⚠️ **Одной командой это сделать нельзя.** `deploy-local.sh --all` обновляет
сайт первым, а отдельного флага «только посредник» у него нет. Поэтому два
захода.

---

## Шаг 1. Проверить настройки на сервере (пять минут)

```bash
ssh root@IP_VPS
cd /opt/hexseal/app
grep -E '^(TRUST_PROXY|VAPID_PUBLIC_KEY|VAPID_PRIVATE_KEY|STORAGE_DIR)=' .env.vps
df -h /var/lib/docker
```

Что должно получиться:

| Строка | Как надо | Если не так |
|---|---|---|
| `TRUST_PROXY=true` | есть | **дописать сейчас**, объяснение ниже |
| `VAPID_PUBLIC_KEY=…` и `VAPID_PRIVATE_KEY=…` | есть, не пустые | каждый перезапуск молча отписывает всех от уведомлений |
| `STORAGE_DIR` | строки нет вообще | если кто-то вписал свой путь — переписка умрёт при следующем обновлении |
| свободного места | больше 2 ГБ | сервер начнёт отказывать в приёме файлов |

### Про `TRUST_PROXY=true` — это важнее остального

Замер: пустил через сервер **340 разных людей за минуту**, у каждого свой
кошелёк и свой интернет.

```
без этой строки: обслужено 300, отказано 40
с этой строкой:  обслужено 340, отказано 0
```

Причина: за туннелем Cloudflare сервер видит вместо всех людей **один адрес**,
и лимит «300 обращений в минуту», рассчитанный на одного человека, становится
общим на всю биржу. При открытом чате вкладка спрашивает сервер раз в пять
секунд — то есть **человек двадцать пять с открытым чатом съедают лимит всех
остальных**.

## Шаг 2. Сделать копию переписки — обязательно

Переписка лежит не в папке, а в **томе Docker**. Скопировать её можно только
изнутри контейнера, обычным `cp` не получится.

```bash
ssh root@IP_VPS "cd /opt/hexseal/app && docker compose stop relayer"
ssh root@IP_VPS "docker run --rm -v relayer_storage:/s -v /tmp:/out alpine \
  tar czf /out/relayer-storage-\$(date +%F).tgz -C /s ."
scp root@IP_VPS:/tmp/relayer-storage-*.tgz ./
tar tzf relayer-storage-*.tgz | grep -c .
```

Последняя команда напечатает число. **Оно должно быть больше нуля.**
Напечатала `0` — копия пустая, дальше не идти.

---

## Шаг 3. Обновить посредника (первым)

```bash
cd ~/Hexseal
scp root@IP_VPS:/opt/hexseal/app/.env.vps /tmp/hexseal-deploy.env
set -a; source /tmp/hexseal-deploy.env; set +a
docker build -t hexseal-relayer --build-arg CACHEBUST="$(date +%s)" ./relayer
docker save hexseal-relayer | ssh root@IP_VPS \
  "docker load \
   && docker tag hexseal-relayer:latest ghcr.io/hexseal/relayer:latest \
   && cd /opt/hexseal/app \
   && docker compose up -d --force-recreate relayer \
   && docker image prune -f"
rm -f /tmp/hexseal-deploy.env
```

## Шаг 4. Убедиться, что посредник новый — ДО сайта

```bash
curl -s https://api.hexseal.net/keys/0x0000000000000000000000000000000000000001
```

**Правильный ответ** — вот такая строка:

```
{"error":"No chat key on file for this address","code":"key_not_found"}
```

**Неправильный** — кусок веб-страницы со словами `Cannot GET /keys`. Значит
работает старый посредник, обновление не доехало.

Если ответ неправильный — **сайт не обновлять**. Ничего откатывать не надо:
старый сайт продолжает работать как работал.

---

## Шаг 5. Обновить сайт (вторым)

```bash
cd ~/Hexseal
bash deploy-local.sh
```

Дождаться строки `✓ BUILD_ID совпал`.
Если написало `❌ НА СЕРВЕРЕ НЕ ТА СБОРКА` — повторить: `bash deploy-local.sh --fresh`.

---

## Шаг 6. Проверить, что всё живо

```bash
curl -s https://api.hexseal.net/health
```

В ответе должен быть кусок `"storage":{"indexTrusted":true`.

- Куска нет вовсе → работает старый посредник.
- Ответ `503` → либо места меньше 2 ГБ, либо сервер не доверяет своей описи.
  Дальше не идти, смотреть журнал: `ssh root@IP_VPS "cd /opt/hexseal/app && docker compose logs --tail 100 relayer"`.

---

## Шаг 7. Убрать мусор от снесённого бота (можно назавтра)

```bash
ssh root@IP_VPS "docker run --rm -v relayer_storage:/s alpine rm -rf /s/xmtp-bot"
```

`xmtp-bot` здесь — **имя каталога на диске**, оставшегося от бота, выключенного
6 августа 2026 вместе со всей обвязкой XMTP. Никакой код в него не смотрит: чат
работает на собственном транспорте, см. `docs/FRONTEND_GUIDE.md`.

---

## Если что-то пошло не так

**Откатывать можно только сайт:**

```bash
cd ~/Hexseal
git checkout main~1
bash deploy-local.sh --fresh
```

⚠️ **Посредника откатывать нельзя.** Старый не знает ни про переписку, ни про
справочник ключей: он их не отдаст и не почистит. Всё, что люди написали
после обновления, останется на диске, но приложение его больше не увидит.
Если дело дошло до этого — сначала снять копию (шаг 2), потом уже трогать.

---

## Чего делать НЕ надо

- **Новых настроек добавлять не нужно.** У посредника появилось 18 новых
  ручек, у каждой в коде записано разумное значение по умолчанию.
- **`docker-compose.yml` не менялся** — копировать на сервер нечего.
- **Переносить старую переписку не нужно.** Она жила в чужой сети и в
  браузерах людей, у нас от неё остаётся только папка бота из шага 7.
