## Fix 1 — `script/Deploy.s.sol` был ловушкой, на которую указывали доки

### Решение: удалить

Скрипт монтировал только 5 фасетов — `DiamondCutFacet`, `DiamondLoupeFacet`,


Диамонд, поднятый этим скриптом, не имел бы доски заказов, доски услуг,

- Скрипт, единственный результат которого — сломанный диамонд, не имеет ни

## Fix 2 — гейт на изменение полей внутри storage-структур

### Почему существующие два гейта не ловят инцидент

Инцидент: коммит `1772ed9` заменил `bytes32 termsHash` на `string terms`
**внутри** `JobBoardStorage.Job` — тот же слот, другая кодировка. Старые
keccak-дайджесты стали читаться как строки с мусорной длиной, `getJob()`
ревертил `Panic(0x22)` на четырёх живых записях.

- `test/StorageLayout.t.sol` пиннит только девять **базовых слотов**
  неймспейсов (`DIAMOND_STORAGE_POSITION` и т.п.) — про содержимое структур
  ничего не знает.
- `script/check-storage-layout.sh` ловит **последовательные state-переменные**
  на фасете (другой класс дефекта — фасет, забывший namespaced-хранилище) —
  структуры внутри namespaced-библиотеки его не касаются вообще.

Смена типа поля внутри `struct Layout`/`struct Data` проходит оба гейта
молча. `docs/CONTRACT_GUIDE.md` уже честно называл это дырой, закрытой только
ревью.

### Дизайн нового гейта

Два файла:

- `script/check-storage-structs.sh` — тонкая bash-обёртка (стиль и
  документация кодов возврата — по образцу `check-storage-layout.sh`),
  вызывает python3.
- `script/check_storage_structs.py` — вся логика: разбор `src/`, сравнение,
  форматирование снапшота, диагностика. Python выбран, а не чистый
  awk/bash, потому что этот же CI-джоб уже требует python3/pip для slither —
  новой зависимости в тулчейне это не добавляет, а получить парсинг корректно
  важнее, чем остаться в одном языке со соседним скриптом (в докстринге файла
  это явно объяснено).

**Обнаружение structs.** Каждая namespaced storage-библиотека находится по
своей doc-аннотации `@custom:storage-location erc7201:` — той же самой,
на которой держится `test/StorageLayout.t.sol` (ровно девять совпадений).
Внутри найденной библиотеки берутся **все** объявления `struct X { ... }` —
и главная структура хранилища (`Layout`/`Data`), и вложенные, которые она
использует как тип поля (`Job`, `Service`, `HireRequest`, `AgreementRecord`,
`JobReceiptData`, `PendingVerdict`, `FacetAddressAndPosition`,
`FacetFunctionSelectors`). Сознательно НЕ делалось «найти тип поля в
Layout/Data и сматчить с именем известной структуры» — это было бы более
хрупким (что если тип написан с лишним пробелом, что если структура
объявлена, но ещё не использована). Взять все структуры внутри помеченной
библиотеки эквивалентно в этой кодовой базе (проверено: `DiamondGuard`
использует эту же аннотацию, но хранит голый `uint256` через inline-assembly
без единого `struct` — скрипт корректно даёт для него ноль структур, это не
ошибка) и надёжнее для будущих правок.

`--print` печатает извлечённую раскладку 16 структур по всем 9 неймспейсам
(3 в `DiamondStorage`, по 2 в `RegistryStorage`/`ReceiptStorage`/
`JobBoardStorage`/`ArbiterRegistryStorage`, 3 в `ServiceBoardStorage`, по 1 в
`FactoryStorage`/`ReputationStorage`) — все восемь вложенных структур из
задания на месте.

**Сравнение.** Текущее извлечение сверяется с закоммиченным
`script/storage-structs.snapshot`. Для каждой структуры старый список полей
должен быть **точным префиксом** нового — единственная мутация, сохраняющая
это свойство, это дописывание полей строго в конец. Смена типа, реордер,
переименование поля, вставка в середину и удаление — все ломают свойство
«префикс» и валят гейт (доказательство ниже). Структура, которой нет по одну
из сторон (новое имя vs. пропавшее старое — для гейта неотличимо от
переименования), тоже проваливает гейт явным списком — молчаливо считать
«новое имя = ОК» было бы дырой: именно так выглядело бы незамеченное
переименование `Job` → `JobV2`.

### Вырожденные случаи (тоже проверены, реальным выводом)

- **Снапшот отсутствует.** Временно перемещён `storage-structs.snapshot` —
  `exit 2`, сообщение прямо говорит «не с чем сравнивать, это не 'чисто' и не
  'ошибка'», с командой для создания базовой линии. Файл возвращён на место.
- **Структур не найдено вообще.** Парсер запущен с `SRC_DIR`, указывающим на
  пустой каталог (без изменения реального `src/`) — `exit 3`, сообщение прямо
  говорит «парсер сломан», перечисляет, каких структур ожидали, явно
  оговаривает «это не то же самое, что структур нет».
- **Структура в src/, которой нет в снапшоте.** Смоделировано через временный
  снапшот в `/tmp` с вручную удалённой записью `JobBoardStorage.Job` (реальный
  `src/` и реальный снапшот не трогались) — `exit 1`, список «есть в src/, но
  нет в снапшоте» с явным упоминанием, что это неотличимо от переименования.

Все три проверены реальным запуском, ни один тестовый артефакт (`/tmp/...`)
не остался и не попал в репозиторий.
